# Log sources

Every device in a network keeps generating logs of what happens on it. These devices are called **log sources**. Their logs are a trail of all activity, useful both for spotting malicious behaviour and for general troubleshooting. Log sources fall into two groups:

```cards
kind: LOG SOURCES
HOST | Host-centric | Events that happen within or relate to a host. Generated by Windows and Linux machines, servers and so on. | Examples: a user accessing a file, a user trying to authenticate, a process running, a process adding, editing or deleting a registry key or value, PowerShell execution.
NET | Network-centric | Generated when hosts talk to each other or reach out to the internet. Generated by firewalls, IDS/IPS, routers and so on. | Examples: an SSH connection, a file accessed over FTP, web traffic, a user reaching company resources through a VPN, network file sharing activity.
```

Together, these two groups create a huge number of logs.

# Why logs alone are not enough

Logging everything sounds good, but with that much traffic the logs become very hard to work through. The room listed five problems:

```cards
kind: CHALLENGES
VOL | Numerous log sources | A network has many log sources producing hundreds of events per second. | The logs are scattered across devices, and checking them one device at a time during an incident is tedious. | warn
CEN | No centralization | Logs stay on the machine that generated them. | The analyst has to connect to each source (SSH, RDP and so on) to read its logs, which wastes valuable time during an investigation. | warn
CTX | Limited context | One log cannot tell the whole story. | A file access on its own looks normal. Correlated with other sources, it might turn out the user reached that machine through lateral movement after compromising another one. | warn
ANL | Limited analysis | Nobody can manually read every log from every device. | Realistically, analysts will miss important logs because there are so many. | warn
FMT | Format issues | Every log source writes logs in its own format. | The analyst would need to know all of them, which gets very hard with many sources. | warn
```

# What a SIEM is

A SIEM is the answer to those problems. It is a security solution that:

```flow
title: What a SIEM does with logs
Collect | Gathers logs from many types of log sources.
Normalize | Converts them into one consistent format.
Correlate | Finds relationships between logs from different sources.
Detect | Uses detection rules to spot malicious activity and raise alerts.
```

# Features of a SIEM

```cards
kind: FEATURES
COL | Centralized log collection | Logs from endpoints, servers, firewalls and other sources are pulled in through lightweight agents or APIs and kept in one place. | No more jumping onto each machine to read its logs.
NRM | Normalization | Raw logs come in different formats and sizes; a Windows log does not look like a Linux log. | Breaking a log into fields is called **parsing**. Converting logs from every source into one consistent format is called **normalization**.
COR | Correlation | Links logs from different sources and looks for patterns between them. | Individual logs are not very useful on their own; the pattern across them is what reveals malicious activity.
ALR | Real-time alerting | Detection rules decide what is malicious. Many come with the SIEM by default, and analysts write new ones to mature future detections. | When a rule's conditions are met, an alert fires and the analyst investigates it inside the SIEM.
DSH | Dashboards and reporting | The most important component of a SIEM. After logs are ingested and normalized, the analysis is summed up as actionable insights. | SIEMs ship with default dashboards and allow custom ones. Typical panels: alert highlights, system notifications, health alerts, failed login attempts, events ingested count, rules triggered, top domains visited.
```

The room's correlation example was a set of activities on one system within five minutes:

```flow
title: Five minutes on one system
VPN login | A user logs in through the VPN from an IP address they have never used before.
Shared drive | The user opens some documents on a shared drive.
PowerShell | The user runs a PowerShell script.
Outbound | The system makes an outbound network connection.
```

```verdict
Potential data exfiltration | Each step looks fine on its own. Correlated by the SIEM, they point to a possible data exfiltration caused by compromised VPN credentials.
```

Other SIEM features the room mentioned but did not cover in detail: threat intelligence feed integration, long data retention and powerful search.

# What logs look like

Every device logs activity, such as a user visiting a website, connecting over SSH or logging into a workstation. Here is what the logs of a few common devices look like before they reach the SIEM.

## Windows

Windows records events that can be viewed in **Event Viewer** (type Event Viewer in the search bar). Each type of activity has its own unique **event ID**, which makes events easy to examine and track. Logs from all Windows endpoints are forwarded to the SIEM for monitoring and better visibility.

## Linux

Linux stores events, errors, warnings and so on in log files that are ingested into the SIEM for continuous monitoring. Common locations:

```cards
kind: LINUX LOGS
HTTP | /var/log/httpd | HTTP requests, responses and error logs.
CRON | /var/log/cron | Events related to cron jobs.
AUTH | /var/log/auth.log and /var/log/secure | Authentication-related logs.
KERN | /var/log/kern | Kernel-related events.
```

The room showed a sample of cron logs: the cron daemon starting, finding no timestamp for the hourly, daily, weekly and monthly root jobs, and failing to send a job's output by mail.

```text
May 28 13:04:20 host crond[2843]: /usr/sbin/crond 4.4 dillon's cron daemon, started with loglevel notice
May 28 13:04:20 host crond[2843]: no timestamp found (user root job sys-hourly)
May 28 13:04:20 host crond[2843]: no timestamp found (user root job sys-daily)
Jun 13 07:46:22 host crond[3592]: unable to exec /usr/sbin/sendmail: cron output for user root job sys-daily to /dev/null
```

## Web server

Every request and response going in and out of a web server should be monitored for possible web attacks. On Linux, Apache logs are usually written to `/var/log/apache` or `/var/log/httpd`. Each line of the room's Apache sample held the client address, a timestamp, the request (`GET /cgi-bin/try/ HTTP/1.0`), the status code (`200`), the response size and the user agent (a Chrome browser in one line, `curl` in the other).

# Log ingestion

Each SIEM has its own way of taking in logs. The common methods:

```cards
kind: INGESTION
AGT | Agent / forwarder | A lightweight tool installed on the endpoint (Splunk calls it a forwarder). | It is configured to capture the important logs and send them to the SIEM server.
SYS | Syslog | A widely used protocol for collecting data from systems such as web servers and databases. | It sends data in real time to a central destination.
UPL | Manual upload | Some SIEMs, such as Splunk and ELK, let you ingest offline data for quick analysis. | Once ingested, the data is normalized and ready for analysis.
PRT | Port forwarding | The SIEM listens on a certain port. | Endpoints forward their data to the SIEM on that listening port.
```
